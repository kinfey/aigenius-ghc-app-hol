# 实验三：创建点餐工作流画布

[English](https://kinfey.github.io/aigenius-ghc-app-hol/lab3/) · [实验二](../lab2/zh.html) · [工作坊首页](../zh.html)

**目标：**在 Copilot App 中使用 `/create-canvas` 创建共享交互式点餐工作流，使用实验二的 MCP 连接。默认模拟运行；真实下单和支付必须分别由用户决定。建议 60 分钟。

![在浏览器中截取的 GitHub 画布公开文档](images/canvas-doc.png)
*参考：[画布扩展文档](https://docs.github.com/en/copilot/how-tos/github-copilot-app/working-with-canvas-extensions)。这里是 App 画布，不是 Power Apps 画布。*

## 1. 设计工作流

1. 打开**同一本地项目会话**，确认实验二的 `mcd-mcp` 已连接。选择 **Plan**，开发时使用模拟商品和虚构地址。
2. 工作流显示 **选餐 → 就餐方式/门店 → 地址（仅配送）→ 优惠 → 价格核对 → 用户确认 → 支付跳转 → 状态**。到店取餐跳过地址；配送需要地址。可用工具及参数以实时服务器为准，不要自行猜测。
3. 明确角色：画布是可视化共享状态和 Agent 可调用的操作界面；Agent 在用户批准后发现并调用单独配置的 MCP 工具。画布按钮不会自动成为 MCP 调用。实验一的网页应用仍是独立应用，不要假定它可访问 App 的 MCP 连接。
4. 默认采用**模拟运行**和虚构数据。不要把真实 Token、地址或支付链接存入共享画布文件、源码、日志或截图。任何修改账户的操作都需要明确确认。不要收集银行卡信息或自动支付。

## 2. 创建并打开画布

1. 在 App 输入框输入 `/create-canvas`，并附上以下提示词。若技能不可用，更新 App 或检查 **Customize → Skills**；不要替换成其他产品。

   > 为本仓库创建项目级交互式点餐工作流画布。使用 create-canvas 技能规定的脚手架、重新加载和验证流程。展示选餐、就餐方式和门店、仅配送时需要的地址、可用优惠、价格核对、用户确认、支付跳转和状态。提供用户控件以及可供 Agent 调用的操作，共同查看和更新状态。默认使用虚构数据模拟运行，只在项目中持久化不含敏感信息的草稿，并明确区分实时与模拟结果。Agent 使用现有 mcd-mcp 连接，调用前发现工具 schema；画布不能保存或直接暴露 Token。每个修改账户的操作都需要新的明确确认。绝不自动创建订单、自动付款或收集支付信息。提供无障碍控件、明确错误和重置功能，并测试操作、状态持久化、到店和配送两条路径。

2. 被询问时选择 **repository/project scope**，使扩展可与工作坊项目共享。审核生成的文件，尤其是 `.github/extensions/<name>/extension.mjs`；只批准理解的命令。Agent 应遵循已安装技能的脚手架、重载、发现、打开、调用及无效输入验证流程。
3. 右侧面板打开后，确认画布和对话看到同一草稿。通过控件添加模拟商品，选择到店或配送并填写虚构地址。请 Agent 通过公布的操作检查草稿，再从对话中更新，确认面板同步变化。
4. 关闭并重新打开画布或重载扩展，确认非敏感草稿仍存在。切换到店/配送，确保只对配送校验地址。测试键盘操作、参数校验、重置和可见错误。若发现或调用失败，请 Agent 检查扩展状态/日志并修复。

## 3. 将工作流连接到真实只读工具

1. 请 Agent 检查实时 MCP 工具列表，并将可用工具映射到各阶段。服务方列出的示例包括 `query-nearby-stores`、`delivery-query-addresses`、`delivery-query-stores`、`query-meals`、`query-store-coupons` 和 `calculate-price`；schema、权限和可用性可能变化。
2. 先使用虚构草稿和不需要个人信息的只读调用。若需真实配送地址，请明确选择是否使用自己的已保存地址；不要请求或展示在公开产物中。查询优惠和菜单之前可能需要选择门店。
3. 让 Agent 在画布中展示实际菜单、可用优惠、商品选项和价格计算。核对商品规格、就餐方式、门店、配送费、优惠和总额。如不可用，应显示错误或明确标注的模拟结果，不得编造实时价格。服务确认前不要假设所选优惠一定适用。

## 4. 真实下单前确认或停止

1. 工作坊默认完成方式是**停在核对页面**。模拟支付跳转只使用虚构链接或状态，不调用真实 `create-order`。
2. 可选：仅当你确实需要真实订单且接受可能产生的费用时，先核对最终详情，再**重新明确确认**调用一次 `create-order`。服务器可能返回支付链接。缺少信息或确认时应停止，不要猜测。请求失败或结果不确定时不要自动重试，应先查询订单状态以免重复下单。
3. 只在私密上下文向订单所有者展示支付链接，由用户自行打开服务方支付页面并决定是否付款。不要收集凭据、自动提交支付，也不要因生成链接就声称支付成功。权限允许时可通过 `query-order` 查询实际状态。遵守取消政策；取消订单也要单独确认。
